## Сверка по официальной документации (не предположения)

Первоисточники:
- Обзор https://dev.max.ru/docs-api
- Формат Update https://dev.max.ru/docs-api/objects/Update
- Подписки https://dev.max.ru/docs-api/methods/POST/subscriptions
- Отправка https://dev.max.ru/docs-api/methods/POST/messages
- Официальная OpenAPI схема https://github.com/max-messenger/api-schema/blob/main/schema.yaml

Подтверждено:
- MAX API base `https://platform-api2.max.ru`.
- Header авторизации `Authorization: <access_token>` (без Bearer); query token не поддерживается.
- `POST /messages?chat_id=...` или `?user_id=...`, JSON `{"text":"..."}`.
- Text максимум 4000 символов; не более 2 сообщений в секунду в один диалог.
- `POST /subscriptions`, HTTPS 443, корректная цепочка TLS.
- Подписка с `secret` отправляет `X-Max-Bot-Api-Secret` в webhook;
  `secret` по документации `^[a-zA-Z0-9_-]{5,256}$`.
- Webhook обязан отвечать `200` в течение 30 секунд; другие ответы/timeout
  считаются ошибкой доставки. Не следует ждать долгой работы модели до ACK.
- `message_created` -> `message.sender.user_id`, `message.recipient.chat_type`
  (`dialog|chat|channel`), `message.body.text`, `message.body.mid`.
- `bot_started` -> `chat_id` и `user.user_id`.
- **ВАЖНО:** в официальной схеме `Recipient.chat_id` nullable/optional;
  `Recipient.user_id` тоже nullable. Нельзя считать наличие `chat_id`
  гарантированным для *всех* личных событий: расследовать допустимый
  fallback для личных сообщений и уметь отправлять по `user_id`.
- ID (`chat_id`, `user_id`) = int64: не переводить в небезопасные JS numbers.

## Обнаруженные риски в коммите (закрыть до реального подключения)

### P0 — надёжность входящих / потеря сообщений

1. `agent/lib/max-webhook.ts`: `if (!deps.dedup.claim(event.dedupKey)) return ok()`
   подтверждает дубль HTTP 200 даже если **первый запрос ещё обрабатывается**.
   Если первый затем падает, ранее подтверждённый дубль уже не будет повторён.
   Обеспечить согласованное состояние `pending/accepted/failed`; конкурентные
   запросы не должны давать ложный ACK.
2. `agent/lib/max-updates.ts`: дедуп только RAM (TTL 1h), теряется при
   рестарте. Нужен устойчивый к перезапуску журнал событий / durable ingress,
   хранение под `data/` (untracked), безопасная обработка crash/replay. Не
   утверждать exactly-once для LLM-ходов без подтверждённого контракта Eve.
3. Установить контракт успешного ACK: `200` только после **надёжного**
   сохранения/принятия события, а не до. Проверить реально, что обеспечивает
   `send()` Eve 0.27.13, включая crash recovery. Не держать webhook в ожидании
   генерации модели дольше 30 с.

### P0 — безопасность тела webhook

4. `agent/lib/max-webhook.ts`: проверка Content-Length не защищает,
   потому что `await request.text()` читает всё тело *до* `raw.length`
   проверки. Внедрить ограниченное потоковое чтение **по байтам**, включая
   chunked/неверный Content-Length, лимит времени и отмену, затем парсить.
   Добавить тест на поток больше лимита без заголовка.

### P1 — исходящие ответы и лимит

5. `agent/channels/max.ts` ловит ошибку отправки и только логирует:
   модель уже ответила, но пользователь ничего не получил. Нужны заметное
   состояние недоставленного сообщения и повторная доставка с лимитом,
   отдельный outbound retry/outbox, если обеспечивается надёжность. Нельзя
   называть результат успешным, пока ответ не дошёл.
6. `agent/lib/max-api.ts`: `lastSent` обновляется только после сетевой
   отправки. Параллельные `sendText()` для одного чата одновременно видят
   одинаковое старое значение и могут нарушить лимит 2/с. Нужна
   сериализация per-dialog, тест с Promise.all.
7. Повтор POST /messages при timeout/сетевом сбое может дать дубликат,
   если MAX фактически создал сообщение, но ответ потерялся. Явно определить
   семантику доставок, проверить наличие официального ключа
   идемпотентности, не обещать exactly-once без поддержки платформы.

### P1 — схема событий, интеграционные тесты и диагностика

8. Добавить тесты на nullable `message.recipient.chat_id`, большие int64,
   отрицательные ID чатов, `bot_started`, неправильную схему, различие
   private/chat/channel. Не подменять официальную схему упрощённым mock.
9. Убедиться, что `/new` реально сбрасывает *существующую* Eve-сессию MAX
   (в Telegram ранее был баг двойного namespace); отдельный интеграционный тест
   на построенной версии Eve, не только заглушка `reset`.
10. Документировать 4 падающих legacy-теста. Повторить на **одинаковом**
    Node 24 окружении для `main` и feature branch; отсутствие регрессии
    подтвердить воспроизводимым логом, а не предположением.
11. Убедиться, что nginx/HTTPS публикует только `/eve/v1/max` и не открывает
    внутренний control API Eve, нет регистрации внешнего webhook без разрешения.
12. Ключи и личные данные только `.env`/`data/`, не в git; команда
    `git diff --check` + проверка gitignore и секретов.
